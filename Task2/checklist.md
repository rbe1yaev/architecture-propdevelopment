# Проверочный лист безопасности бизнес-систем PropDevelopment

| № | Вопрос | Да/нет | Комментарий |
|---|---|---|---|
| **I. Управление доступом** | | | |
| 1 | Используется ли многофакторная аутентификация (MFA) для доступа к критическим системам и сервисам? | Нет | Keycloak (auth-service-1) развёрнут для покупателей и собственников и поддерживает MFA, но её применение не подтверждено. Для финансового домена (accountant-service) и административных консолей MFA не используется. **Рекомендация:** включить MFA для всех критических сервисов, администраторов Kubernetes, доступа к accountant-service и Active Directory. |
| 2 | Настроены ли требования к сложности паролей и их регулярное обновление? | Частично | Keycloak имеет встроенные политики паролей. Однако единая политика для всех систем (Keycloak, AD, accountant-service) не утверждена. **Рекомендация:** утвердить единую политику паролей (длина ≥ 12 символов, сложность, срок действия 90 дней) и применить её во всех IdP. |
| 3 | Проводится ли аудит и пересмотр учётных записей с повышенными привилегиями на регулярной основе? | Нет | Service accounts используются для межсервисного взаимодействия (REST между client-crm-app, client-mart-app, tenant-core-app). Процесс аудита и ресертификации привилегированных учёток отсутствует. **Рекомендация:** внедрить PAM-решение; проводить ежеквартальный аудит привилегированных учёток; настроить автоматическую ротацию credentials. |
| 4 | Реализован ли принцип минимальных привилегий при назначении ролей и прав доступа? | Нет | Менеджеры имеют доступ ко всем клиентам, что подтверждается жалобами на cross-tenant доступ (отображение чужих данных в ЛК). Системы обращаются друг к другу напрямую без RBAC-прослойки. **Рекомендация:** внедрить единую RBAC-модель; разграничить доступ по доменам (Продажи, ЖКУ, Финансы) и ролям (менеджер, аналитик, администратор). |
| 5 | Автоматически ли удаляются или деактивируются учётные записи после увольнения или изменения должности сотрудников? | Частично | Active Directory используется для финансового домена, что позволяет деактивировать учётки. Для клиентских систем (Keycloak для покупателей и собственников) процесс деактивации не описан. **Рекомендация:** настроить интеграцию Keycloak с HR-системой для автоматической деактивации; внедрить регулярный аудит активных учётных записей. |
| 6 | Ведётся ли журналирование всех операций доступа к системам и данным? Кто имеет доступ к журналам? | Нет | Журналирование доступа к системам и данным не централизовано. Логи собираются фрагментарно. Доступ к журналам не регламентирован. **Рекомендация:** внедрить SIEM-систему; централизовать сбор логов доступа из всех систем; настроить RBAC на доступ к журналам. |
| 7 | Используются ли механизмы контроля доступа на основе атрибутов для повышения гибкости управления доступом? | Нет | ABAC не используется. Разграничение доступа строится на прямых связях между сервисами (REST-вызовы без промежуточного контроля). **Рекомендация:** внедрить Policy Engine (O PA, Open Policy Agent) для реализации ABAC; централизовать политики доступа к данным. |
| 8 | Используются ли системы аутентификации пользователей для доступа к системам? | Частично | Keycloak (auth-service-1) используется для аутентификации покупателей и собственников. Active Directory — для финансового домена. Единая система аутентификации отсутствует. **Рекомендация:** объединить Keycloak-инстанции или настроить федерацию; подключить AD к Keycloak через LDAP-бридж. |
| 9 | Созданы ли замкнутые контуры для подсистем, работающих с чувствительными данными? | Нет | Данные передаются между системами напрямую (client-crm-app ↔ client-mart-app, tenant-core-app ↔ CRM). Замкнутые контуры для ПДн не выделены. **Рекомендация:** выделить замкнутый контур Processing для ПДн; изолировать его от общего трафика с помощью Network Policies и сегментации. |
| 10 | Ограничен ли доступ к системам из внешних источников? | Частично | Firewall установлены на входе в группы сервисов (см. C4-диаграмму). Внешние подключения к БД не описаны. API-интеграции с партнёрами выполняются напрямую из микросервисов. **Рекомендация:** закрыть прямой доступ к БД извне; внедрить API Gateway для всех внешних вызовов. |
| 11 | Ведётся ли единый реестр учётных записей? | Нет | Учётные записи распределены по нескольким системам: Keycloak (покупатели), Keycloak (собственники), Active Directory (финансы). Единый реестр отсутствует. **Рекомендация:** внедрить единый каталог учётных записей на базе Keycloak или Azure AD; настроить автоматическую синхронизацию между IdP. |
| 12 | Используются ли средства управления учётными записями на базе единого реестра? | Нет | Ввиду отсутствия единого реестра (п. I.11) средства управления на его базе не применяются. **Рекомендация:** после внедрения единого реестра настроить централизованное управление жизненным циклом учётных записей (создание, блокировка, удаление). |
| 13 | Применяются ли средства для отзыва прав доступа? | Частично | Active Directory позволяет отзывать доступ в финансовом домене. Keycloak поддерживает отзыв сессий, но централизованный процесс отзыва прав не реализован. **Рекомендация:** внедрить централизованное управление отзывом прав; настроить автоматический отзыв при инцидентах. |
| 14 | Используются ли средства централизованного контроля доступа? | Нет | Каждая система управляет доступом самостоятельно. Централизованный Policy Decision Point (PDP) отсутствует. **Рекомендация:** внедрить централизованную платформу контроля доступа (Keycloak Authorization Services, Axiomatics); настроить единую точку принятия решений о доступе. |
| **II. Безопасность данных** | | | |
| 1 | Разработана ли политика классификации данных, и актуализируется ли она в соответствии с действующим законодательством? | Нет | Политика классификации отсутствует. Данные не маркируются по категориям (см. Задание 1 — mindmap как первая попытка классификации). **Рекомендация:** утвердить политику классификации данных по ISO/IEC 27001; внедрить автоматическую маркировку данных на основе контента (DLP-решения). |
| 2 | Используется ли шифрование на уровне базы данных, файловой системы и при передаче данных по сети? | Частично | TLS для внешних каналов вероятно используется. Внутренние межсервисные вызовы (SpringBoot → SpringBoot, JDBC) не имеют подтверждения шифрования. TDE для MSSQL (crm-db) и шифрование на уровне ФС для PostgreSQL не описаны. **Рекомендация:** включить mutual TLS для всех внутренних вызовов; включить TDE для MSSQL и LUKS для PostgreSQL-хостов. |
| 3 | Реализованы ли механизмы управления ключами шифрования? | Нет | Управление ключами шифрования не описано. KMS или HSM не упоминаются. **Рекомендация:** внедрить KMS (HashiCorp Vault, AWS KMS); хранить мастер-ключи в HSM; настроить автоматическую ротацию ключей каждые 90 дней. |
| 4 | Проводится ли регулярное резервное копирование данных? Хранятся ли резервные копии в защищённых хранилищах? | Частично | Данные передаются в DWH (Greenplum → S3), что может выполнять роль резервирования, но RPO/RTO не определены. Регламент бэкапов не разработан. **Рекомендация:** внедрить централизованную политику бэкапов (pgBackRest для PG, Veeam для MSSQL); определить RPO ≤ 1 ч, RTO ≤ 4 ч. |
| 5 | Выполняется ли регулярное тестирование процесса восстановления данных из резервных копий? | Нет | Тестирование восстановления не проводится. **Рекомендация:** проводить ежемесячное тестирование восстановления из бэкапов; фиксировать результаты в отчётах. |
| 6 | Ограничен ли доступ к резервным копиям данных, и зашифрованы ли они? | Нет | Доступ к резервным копиям не регламентирован. Шифрование бэкапов не описано. **Рекомендация:** зашифровать все резервные копии; ограничить доступ по RBAC; хранить копии в географически распределённых дата-центрах. |
| 7 | Ведётся ли учёт персональных данных, и применяются ли специальные процедуры обработки и хранения для различных типов данных? | Нет | ПДн обрабатываются напрямую в client-crm-app, client-mart-app, tenant-core-app. Реестр ПДн не ведётся. Специальные процедуры для разных типов данных не определены. **Рекомендация:** составить реестр ПДн (категории, системы хранения, сроки); разработать процедуры обработки для каждого типа данных. |
| 8 | Осуществляется ли мониторинг доступа к данным на основе их классификации? Используются ли метки безопасности для маркировки данных? | Нет | Классификация не внедрена (п. II.1), метки безопасности не используются. Мониторинг доступа на основе классификации невозможен. **Рекомендация:** внедрить систему управления метаданными; настроить автоматическое присвоение меток безопасности на основе контента. |
| 9 | Разработаны ли процессы и системы Data Governance для управления данными? | Нет | Data Governance не внедрён. Нет единого владельца данных (data owner) для каждого домена. **Рекомендация:** внедрить Data Governance Council; назначить data owners для каждого домена (Продажи, ЖКУ, Финансы); разработать политики качества данных. |
| 10 | Реализованы ли системы или процессы безопасного уничтожения данных? | Нет | Процессы безопасного уничтожения данных не описаны. При утилизации оборудования или удалении ПДн клиентов (по 152-ФЗ) гарантии отсутствуют. **Рекомендация:** внедрить процедуры безопасного удаления данных (DoD 5220.22-M для HDD, crypto erase для SSD); настроить автоматическое удаление ПДн по запросу субъекта. |
| 11 | Используются ли системы или процессы контроля целостности данных? | Нет | Контроль целостности данных (контрольные суммы, цифровые подписи) не реализован для потоков данных между системами (CDC, Kafka). **Рекомендация:** внедрить checksum-верификацию для CDC-потоков; использовать цифровые подписи для критических документов (контракты, акты). |
| 12 | Реализованы ли системы или процессы контроля сохранности данных? | Частично | Данные сохраняются в DWH (Greenplum → S3), механизмы контроля сохранности описаны фрагментарно. **Рекомендация:** внедрить мониторинг целостности хранилищ (S3 Object Lock, Greenplum checksums); настроить алерты на нарушение сохранности. |
| 13 | Применяются ли средства или процессы анонимизации данных? | Нет | Механизмы анонимизации/обезличивания ПДн не внедрены. BI-аналитики работают с полными данными клиентов. **Рекомендация:** внедрить токенизацию ПДн; псевдонимизировать данные в DWH; настроить обезличивание при передаче данных в BI-аналитику. |
| 14 | Разработана ли инструкция по процессу восстановления данных? | Нет | Инструкция по восстановлению данных не разработана. **Рекомендация:** разработать Disaster Recovery Plan (DRP); включить сценарии восстановления для каждой БД, DWH и S3-хранилища. |
| **III. Защита инфраструктуры** | | | |
| 1 | Используется ли межсетевой экран для ограничения входящего и исходящего трафика? | Частично | Firewall присутствуют на входе в группы сервисов (см. C4-диаграмму). Внутренние правила не описаны. **Рекомендация:** провести аудит FW-правил; установить запрет по умолчанию на весь трафик и разрешать только явно необходимый. |
| 2 | Реализована ли сегментация сети на логические зоны (DMZ, корпоративная сеть, гостевая сеть) для ограничения доступа к критическим ресурсам? | Частично | В C4-диаграмме отражены две группы сервисов (Продажи, ЖКУ) с firewal. Внутренняя сегментация между доменами (Продажи / ЖКУ / Финансы / Данные) не показана. **Рекомендация:** внедрить микросегментацию; изолировать сети по доменам с помощью Network Policies в Kubernetes и VLAN. |
| 3 | Используются ли IDS/IPS-системы для обнаружения и предотвращения сетевых атак? | Нет | IDS/IPS не упоминаются в описании инфраструктуры. **Рекомендация:** внедрить Network IDS (Suricata, Zeek) на границах сегментов; настроить интеграцию с SIEM. |
| 4 | Настроен ли мониторинг сетевого трафика на предмет аномалий и возможных атак, например, DDoS? | Нет | Мониторинг трафика на аномалии не описан. **Рекомендация:** настроить NetFlow/sFlow мониторинг; внедрить систему обнаружения DDoS-атак; подключить Anti-DDoS от провайдера. |
| 5 | Проводится ли регулярное сканирование уязвимостей операционных систем, приложений и сетевых устройств? | Частично | Используются современные технологии (SpringBoot, PostgreSQL), но процедуры patch management и сканирования уязвимостей не описаны. **Рекомендация:** внедрить автоматическое сканирование уязвимостей (Trivy для контейнеров, Nessus для хостов); настроить процесс приоритетного исправления критических уязвимостей. |
| 6 | Установлены ли на серверах и рабочих станциях антивирусные программы и системы EDR? | Нет | Средства защиты endpoint не упоминаются. **Рекомендация:** внедрить EDR-решение (например, Kaspersky Endpoint Security, CrowdStrike) на всех серверах и рабочих станциях; настроить централизованное управление обновлениями сигнатур. |
| 7 | Отключены ли неиспользуемые службы и порты на серверах, рабочих станциях и сетевом оборудовании? | Частично | В C4 указаны открытые порты для REST, JDBC, CDC, Kafka. Аудит на предмет неиспользуемых портов не проводился. **Рекомендация:** провести аудит открытых портов; закрыть все неиспользуемые порты; внедрить принцип минимального сетевого доступа. |
| 8 | Используются ли механизмы контроля целостности системных файлов? Ведётся ли журналирование доступа к системным ресурсам? | Нет | Контроль целостности системных файлов (AIDE, Tripwire) не описан. **Рекомендация:** внедрить FIM (File Integrity Monitoring) на критических серверах и Kubernetes-хостах; централизовать логи доступа к системным ресурсам. |
| 9 | Проводятся ли автоматизированные сканирования облачных инфраструктур на соответствие рекомендациям безопасности? | Нет | Облачная инфраструктура (при её наличии) не сканируется. CIS-бенчмарки для Kubernetes и PostgreSQL не проверяются. **Рекомендация:** внедрить автоматическое сканирование на соответствие CIS benchmarks (kube-bench для Kubernetes, pgAudit для PostgreSQL); подключить CSPM при использовании облаков. |
| 10 | Реализовано ли автоматическое обновление сигнатур защиты от вредоносных программ? | Нет | EDR/AV не внедрены (п. III.6), следовательно, автоматическое обновление сигнатур не настроено. **Рекомендация:** после внедрения EDR настроить автоматическое обновление сигнатур; тестировать обновления перед развёртыванием на продуктивные системы. |
| 11 | Осуществляется ли фильтрация трафика между сетевыми сегментами? | Частично | Фильтрация на уровне firewall между внешней сетью и группами сервисов присутствует. Внутренняя фильтрация между доменами не реализована. **Рекомендация:** реализовать фильтрацию трафика между всеми сетевыми сегментами; использовать Network Policies для Kubernetes. |
| 12 | Используются ли средства для контроля периметра доступа? | Частично | Firewall на входе — да. API Gateway для контроля внешнего доступа — нет. VPN для административного доступа не описан. **Рекомендация:** внедрить API Gateway для периметрального контроля; настроить VPN (WireGuard, OpenVPN) для административного доступа. |
| **IV. Управление инцидентами** | | | |
| 1 | Используется ли система мониторинга безопасности (SIEM) для корреляции событий и анализа аномалий в режиме реального времени? | Нет | SIEM-система не внедрена. Логи собираются фрагментарно, корреляция событий не выполняется. **Рекомендация:** внедрить SIEM (Splunk, Wazuh, MaxPatrol SIEM); подключить все источники — серверы, БД, API Gateway, Kubernetes. |
| 2 | Настроены ли автоматические оповещения об инцидентах и подозрительной активности (например, попытках несанкционированного доступа)? | Нет | Оповещения не настроены. **Рекомендация:** настроить корреляционные правила в SIEM; определить пороги алертов (N неудачных логинов за M минут, передача данных за пределы сегмента); настроить интеграцию с Telegram/E-mail/Slack. |
| 3 | Разработан ли план реагирования на инциденты, включающий анализ, эскалацию и восстановление системы? Проводится ли обучение сотрудников? | Нет | IRP (Incident Response Plan) не разработан. Обучение сотрудников не проводится. **Рекомендация:** разработать IRP, включающий этапы: обнаружение, сдерживание, ликвидация, восстановление, извлечение уроков; определить состав CSIRT; проводить ежегодное обучение. |
| 4 | Проводятся ли симуляции инцидентов (учения) для проверки готовности сотрудников к реагированию на кибератаки? | Нет | Учения не проводятся. **Рекомендация:** организовать ежегодные Tabletop Exercises; привлекать сторонние компании для Red Team-оценок и penetration testing. |
| 5 | Ведётся ли статистика по всем зарегистрированным инцидентам и используются ли результаты анализа для корректировки политики безопасности? | Нет | Реестр инцидентов не ведётся. Анализ для корректировки политик не проводится. **Рекомендация:** внедрить реестр инцидентов с категоризацией (тип, критичность, время обнаружения, время устранения, root cause); ежеквартально анализировать тренды и корректировать политики. |
| 6 | Как часто проводятся внутренние и внешние аудиты безопасности? Обновляются ли политики и процедуры на основе результатов этих аудитов? | Нет | Аудиты не проводятся (данный чек-лист — первый). Политики и процедуры безопасности не разработаны. **Рекомендация:** проводить внутренний аудит раз в полугодие; внешний аудит — раз в год; привлекать сертифицированных аудиторов по ISO/IEC 27001. |

Удалённый доступ сотрудников к внутренним системам (CRM, AD) через VPN не описан. **Рекомендация:** настроить VPN (WireGuard, OpenVPN) для удалённого доступа сотрудников; использовать клиентские сертификаты для аутентификации VPN. |
| 3 | Проводится ли автоматическое выявление и ограничение использования незарегистрированных или неавторизованных устройств в сети? | Нет | NAC (Network Access Control) не используется. Неавторизованные устройства могут подключаться к корпоративной сети. **Рекомендация:** внедрить NAC (Cisco ISE, Aruba ClearPass); настроить автоматическую блокировку неавторизованных устройств. |
| 4 | Настроены ли политики автоматического резервного копирования в облачной среде? Однако политики не формализованы. **Рекомендация:** настроить автоматические политики бэкапа S3 (версионирование, жизненный цикл); зашифровать резервные копии; ограничить доступ по IAM-политикам. |
| **V.2. Управление оборудованием и физической безопасностью** | | | |
| 1 | Используются ли системы контроля доступа — биометрия, СКУД — в серверных помещениях? | Частично | Инфраструктура (серверы, СХД) размещается в дата-центрах (Cloud/on-premise не уточнено). Физический доступ со стороны инженеров дата-центра вероятно контролируется, но собственные серверные помещения не описаны. **Рекомендация:** при наличии собственных серверных внедрить СКУД + видеонаблюдение; при аренде ЦОД — запросить сертификаты физической безопасности (SOC 2, PCI DSS AOC). |
| 2 | Ведётся ли инвентаризация всего оборудования? | 3 | Используются ли безопасные методы удаления данных перед утилизацией оборудования или передачей в другие подразделения? | Нет | Процедуры безопасного удаления данных при утилизации не описаны. **Рекомендация:** внедрить процедуры: DoD 5220.22-M для HDD, factory reset + crypto erase для SSD/ноутбуков; составлять акты об утилизации. |
