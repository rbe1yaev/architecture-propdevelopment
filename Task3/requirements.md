# Требования к интеграции сервисов «Умный дом»

## Контекст

PropDevelopment расширяет функциональность мобильного приложения собственников, добавляя интеграцию с партнёрской платформой «Умный дом». В рамках интеграции реализуются два сервиса:

| Сервис | Функциональность | Чувствительные данные |
|--------|-----------------|---------------------|
| **Интеллектуальный домофон** | Открытие двери по звонку + биометрическое распознавание лица | Биометрические данные (изображение лица) |
| **Интеллектуальный шлагбаум** | Управление шлагбаумом + распознавание номеров автомобилей | Номера транспортных средств, привязка к собственнику |

Доступ к сервисам — через текущее мобильное приложение собственников (Витрина сервисов для собственников, iOS/Android).

---

## 1. Требования к безопасности

### 1.1. Шифрование данных при передаче

- Все каналы передачи данных между PropDevelopment и Платформой «Умный дом» должны использовать **TLS 1.3** (минимум TLS 1.2) — защита персональных данных и команд управления от перехвата (MITM). Согласно 152-ФЗ, передача ПДн допускается только по защищённым каналам.
- Для межсервисного взаимодействия внутри контура PropDevelopment использовать **mTLS** (взаимную TLS-аутентификацию) — гарантирует, что запросы исходят от легитимного сервиса, предотвращает подделку источника запроса.
- Все API-эндпоинты партнёрской платформы должны быть доступны исключительно по HTTPS.

### 1.2. Обезличивание и токенизация биометрических данных

- **Биометрические данные (изображения лиц) НЕ должны храниться в системах PropDevelopment.** Распознавание лица выполняется на стороне партнёрской платформы. Биометрия — специальная категория персональных данных (ст. 11 152-ФЗ), хранение требует отдельного согласия и аттестованных средств защиты.
- PropDevelopment передаёт партнёру только **обезличенный референс (токен)** собственника, а не его персональные данные (ФИО, телефон и т.д.) — принцип минимизации передаваемых данных (Least Privilege).
- Биометрические шаблоны (face embeddings) должны храниться партнёром в **зашифрованном виде**, ключи шифрования — в HSM/KMS.
- Реализовать механизм **отзыва биометрических данных** — собственник должен иметь возможность удалить свои биометрические данные через ЛК (требование 152-ФЗ).

### 1.3. Защита номеров транспортных средств

- Номера автомобилей, привязанные к собственнику, должны храниться в системах PropDevelopment в **зашифрованном виде** (AES-256). Номер автомобиля в связке с идентификатором собственника является персональными данными.
- При передаче номера автомобиля партнёру для распознавания использовать **однонаправленный хеш с солью** либо временный токен — партнёр не получает прямого доступа к реестру номеров собственников.

### 1.4. Контроль целостности и защита от подделки команд

- Все критические команды (открытие двери, открытие шлагбаума) должны быть подписаны **HMAC-SHA256** или **цифровой подписью** — предотвращение подмены команд злоумышленником.
- Каждый запрос должен содержать **уникальный nonce** и **временную метку (timestamp)**. Сервер должен отклонять запросы с расхождением времени > 60 секунд — защита от replay-атак.
- Реализовать **идемпотентность** критических операций (idempotency key) — предотвращение дублирования команд при сетевых сбоях.

### 1.5. Соответствие 152-ФЗ «О персональных данных»

- Получить **явное информированное согласие** собственника на обработку биометрических данных и их передачу партнёру (ст. 11 152-ФЗ).
- Все серверы, обрабатывающие ПДн, должны быть **физически расположены на территории РФ** (ч. 5 ст. 18 152-ФЗ).
- Заключить с партнёром **договор поручения** на обработку персональных данных (ст. 6 152-ФЗ).
- Реализовать процедуру **уведомления Роскомнадзора** об обработке биометрических данных (ст. 22 152-ФЗ).

### 1.6. Минимизация передаваемых данных

- Передавать партнёру **минимально необходимый набор данных**: идентификатор собственника (токен), идентификатор устройства, тип команды — без ФИО, телефона, email, адреса.
- Логи интеграции **не должны содержать персональных данных** в открытом виде — использовать маскирование/токенизацию.

## 2. Протоколы аутентификации и авторизации

### 2.1. Аутентификация пользователей (собственников)

- Аутентификация собственника в мобильном приложении через существующий **auth-service-1 (Keycloak)** с поддержкой **OAuth 2.0 + OpenID Connect (OIDC)** — единая точка аутентификации, без дублирования учётных записей.
- Для операций управления домофоном и шлагбаумом применять **повышенный уровень аутентификации (MFA)**: подтверждение через push-уведомление или биометрию устройства (Touch ID / Face ID).
- Access token, выдаваемый Keycloak, должен содержать **scope, ограниченный конкретным устройством** — предотвращение cross-tenant доступа (собственник из ЖК «А» не может открыть дверь в ЖК «Б»).

### 2.2. Авторизация (управление доступом)

- Реализовать **RBAC (Role-Based Access Control)** с ролями: `resident` (собственник), `security` (охрана ЖК), `admin` (управляющая компания).
- Дополнить RBAC моделью **ABAC (Attribute-Based Access Control)** — учитывать атрибуты: `property_id` (привязка к ЖК), `device_id` (конкретное устройство), `time` (временные ограничения).
- Реализовать механизм **временных разрешений (Just-In-Time)** для гостей: собственник может выдать временный доступ на ограниченный срок.

### 2.3. Аутентификация между системами (Service-to-Service)

- Взаимодействие между PropDevelopment и Платформой «Умный дом» — через **OAuth 2.0 Client Credentials Grant** с mTLS.
- **API Keys** для партнёра должны иметь ограниченный срок действия (максимум 90 дней) с автоматической ротацией.
- Реализовать механизм **отзыва (revocation)** токенов и API-ключей в реальном времени через Keycloak Admin API.

## 3. Организация взаимодействия

### 3.1. Архитектура интеграции

Взаимодействие между системами PropDevelopment и внешней платформой «Умный дом» организуется через выделенный микросервис-посредник в домене ЖКУ:

- **smart-home-integration-service** — новый микросервис (Kotlin/SpringBoot), выполняющий функции точки входа для интеграции: аутентификация (проверка JWT из Keycloak), авторизация (RBAC + ABAC), трансляция команд, агрегация статусов, обработка callback от партнёра.
- **smart-home-db** (PostgreSQL) — хранение связей собственник↔устройство, статусов устройств и конфигураций. Данные изолированы от tenant-core-db.

### 3.2. Политики безопасности API

- Все API-контракты с партнёром должны пройти **security review** перед публикацией — проверка на отсутствие избыточных ПДн в полях запросов/ответов.
- Настроить **Rate Limiting** на уровне smart-home-integration-service: не более N запросов в минуту от одного собственника, не более M запросов в минуту к одному устройству.
- Все API должны следовать спецификации **OpenAPI 3.0** с обязательным описанием схем безопасности (securitySchemes).
